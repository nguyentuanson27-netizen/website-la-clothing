## Machine-derived create-order structure

The reproducible envelope records:

- `POST /shops/{SHOP_ID}/orders`;
- required integer path parameter `SHOP_ID`;
- API authentication as query-string `api_key`;
- required `application/json` request body;
- top-level required request property `shop_id`;
- `items[]` requiring `variation_id` and `quantity`;
- integer `variation_info.retail_price` in the selected structural subset;
- selected structured `shipping_address` fields;
- documented response status `200` with `application/json`;
- integer response `id` as the selected Pancake order identity field.

The external request model is broad. This evidence must **not** become a browser-controlled pass-through. The production C8 mapper must use a strict server-owned allowlist built from the local checkout snapshot and freshly revalidated Pancake facts.

## Manual review notes — not generated by the CLI

The following statements come from manual review of descriptions/semantics in the fingerprinted raw document and are deliberately **not** stored in the machine-derived JSON:

- `custom_id: string` is described only as `Custom ID`;
- `account: integer` is described as `Order source ID`;
- `account_name: string` is described as `Order source name`;
- no native idempotency key, uniqueness guarantee, `request_id`, client-reference guarantee, or safe retry contract was identified in the reviewed create-order documentation.

These notes do **not** prove that Pancake lacks such behavior outside the reviewed document. They only mean this project has no trusted evidence authorizing that assumption. Therefore:

- do not treat `custom_id` as an idempotency key;
- do not perform a blind second POST after timeout/network ambiguity;
- the approved one-shot state machine remains valid: durable `POS_SUBMITTING` before the network call → exactly one POST attempt → definitive success `CONFIRMED`, safely classifiable rejection `REJECTED`, ambiguous outcome `SYNC_UNKNOWN`;
- duplicate-safe retry/reconciliation remains blocked until a trustworthy unique reference/idempotency mechanism is separately verified.

The exact request/response structure is therefore no longer the blocker for the one-shot create-order slice. Retry semantics remain blocked.

## Bounded local-file safety boundary

The evidence command:

- opens exactly one developer-selected file once and keeps that same file handle for metadata and content reads;
- rejects a non-file or an initial size above 16 MiB;
- allocates at most 16 MiB + 1 byte for the content read and reads at most that many bytes;
- if the file grows after initial metadata, the extra byte causes `OPENAPI_EVIDENCE_FILE_TOO_LARGE` rather than allowing an oversized parse;
- closes the file handle explicitly on success or failure;
- does not load `.env.local`, read `PANCAKE_API_KEY` / `PANCAKE_SHOP_ID`, instantiate the Pancake HTTP client, make a network request, or issue a Pancake write;
- maps JSON parse and local I/O failures to fixed safe diagnostics without printing parser details or local paths;
- relies on the structural inspector's shared 10,000-work-unit traversal budget after parsing;
- excludes examples, defaults, descriptions and external scalar sample values from emitted evidence.

The command and checked-in evidence are **inspection aids, not write authorization**.
